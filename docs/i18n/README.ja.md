# Codex Tray Manager

[简体中文](../../README.md) · [English](README.en.md) · [日本語](README.ja.md) · [한국어](README.ko.md) · [Español](README.es.md) · [Français](README.fr.md) · [Deutsch](README.de.md) · [Português (Brasil)](README.pt-BR.md)

**複数の Codex インスタンスを、1 つのトレイから。ウィンドウを見つけ、バックグラウンドの状態を把握してから、終了方法を判断できます。**

Windows ですでに分離起動スクリプトを使用しているユーザー向けに、Codex Tray Manager は起動、切り替え、再起動、終了を集約し、タスクバー、スクリプト、タスク マネージャーを行き来する手間を減らします。既存のインスタンスを管理するツールであり、アカウント作成、チャット移行、分離環境の構築は行いません。

> これは非公式のコミュニティ製ツールであり、OpenAI との提携関係も、OpenAI による承認もありません。

Windows 10/11、PowerShell 7、および分離された Codex インスタンスを起動できる PowerShell スクリプトが 1 つ以上必要です。マネージャーは各インスタンス固有の `--user-data-dir` 引数からプロセスの所属を識別します。

<a id="它解决什么问题"></a>

## 解決する課題

1 台の Windows PC で複数の分離された Codex デスクトップインスタンスを実行すると、タスクバー、タスク マネージャー、複数の起動スクリプトを行き来しがちです。非表示のウィンドウは見つけにくく、通常の終了ではウィンドウだけが閉じてバックグラウンドプロセスが残る場合があります。一方、プロセスツリー全体を直接終了すると、アプリの終了を待つ更新スクリプト、ターミナル、その他のタスクまで誤って停止するおそれがあります。

Codex Tray Manager は共通のトレイ操作口を用意し、「アプリ自身のバックグラウンドプロセス」と「用途が未確認の子タスク」を分けて扱います。主な対象は次の課題です。

- 複数の Codex インスタンスに統一された稼働状態表示と操作口がない。
- 非表示ウィンドウやウィンドウのないバックグラウンドプロセスを探し、前面に戻しにくい。
- 正常終了後も Electron、app-server などが残る場合がある。
- プロセスツリーの一括強制終了で更新スクリプト、ターミナル、実行中の作業が中断される。
- 複数バージョンのインスタンスを再起動するとき、直前に実行していたバージョンの組み合わせを復元しにくい。

<a id="功能概览"></a>

## 機能概要

- JSON 設定からインスタンスメニューを動的に生成し、実行中のインスタンスを自動的に上位へ配置します。
- 起動後にメインプロセスが安定して稼働していることを検証し、起動スクリプトの戻り値だけで成功と判断しません。
- 非表示の Electron トップレベルウィンドウを列挙し、復元と前面表示を試み、その結果も確認します。
- 終了時はまずウィンドウに通常の終了を要求し、その後アプリ所属と確認できた残存プロセスを個別に検証して処理します。
- PID と作成時刻の組み合わせでプロセスを識別し、PID 再利用による誤操作のリスクを抑えます。
- 用途不明の子タスクがあると通常終了を阻止し、確認用に名前、PID、作成時刻を表示します。
- 再確認付きの緊急終了と、インスタンスごとの結果をまとめる一括終了を提供します。
- `Standard` と `UICanary` に対応し、再起動時に直前の実行バージョンを復元します。
- 状態更新と終了待機をバックグラウンドスレッドで行い、トレイメニューの応答性を維持します。
- 自動ローテーション付き JSONL 診断ログを記録します。完全なプロセスコマンドラインやログイン認証情報は記録しません。

<a id="先看一个典型使用流程"></a>

## 一般的な操作の流れ

1. 分離インスタンスを最低 1 つ設定します。複数設定する場合、ユーザーデータディレクトリをそれぞれ別にします。
2. トレイで実行中のインスタンスを確認し、必要なウィンドウを前面に戻します。
3. 終了する前にプロセスと終了チェックを確認し、アプリのバックグラウンドと用途未確認の子タスクを区別します。
4. 通常終了を使用します。未確認のタスクが検出された場合は、緊急終了で回避せず、まず理由を確認します。
5. 最近の操作結果を見て、実際に何が完了したか確認します。

このページには、実機のトレイメニューのスクリーンショットや動画はまだありません。上記は操作順序の説明であり、収録済みのデモではありません。また、すべての起動スクリプトや Windows 環境で検証済みであることを意味しません。

<a id="快速开始"></a>

## クイックスタート

次の 3 つを準備してください。

- Windows 10/11 と PowerShell 7（`pwsh`）。従来の Windows PowerShell だけでは不十分です。
- 対象の Codex を単独で起動できる既存の PowerShell スクリプト。
- 各バージョンの起動スクリプトの絶対パスと、一意のユーザーデータディレクトリ。例の `D:\codex4` などをそのまま使用しないでください。

起動スクリプト自体が正常に動かない場合は、トレイマネージャーに組み込む前に解決してください。

通常の利用者は [Releases](https://github.com/son-gladyso/codex-tray-manager/releases) から Windows ポータブル版 ZIP をダウンロードし、展開後に `manager.settings.example.json` を `manager.settings.json` にコピーして、PC 上のパスを入力できます。

開発者はリポジトリをクローンすることもできます。

```powershell
git clone https://github.com/son-gladyso/codex-tray-manager.git
cd codex-tray-manager
Copy-Item manager.settings.example.json manager.settings.json
notepad manager.settings.json
pwsh -NoProfile -File .\CodexTrayManager.ps1 -ValidateOnly
```

検証が通ったら `Start Codex Tray Manager.cmd` をダブルクリックします。マネージャーを終了しても Codex は終了しません。

**初回の成功基準：**設定したインスタンスがトレイメニューに表示され、状態更新後に実行中と停止中を区別できること。実行中で表示されているテスト用インスタンスで「前面に切り替え」を試し、操作結果を確認してください。設定検証の成功は、ウィンドウ切り替えや終了動作の実機受け入れ検証が完了したことを意味しません。まずチェックと結果表示に慣れてから終了操作を試してください。

<a id="日常操作"></a>

## 日常の操作

- 設定内の Codex インスタンス（番号 4–25）をまとめて管理し、実行中のものを上位に表示します。
- 同じインスタンスの通常版と UI 試行版をまとめて管理できます。終了は両方を処理し、再起動は直前に実行していたバージョンを復元します。どちらも停止中なら、既定で通常版を起動します。
- 「起動 / 前面に切り替え」：起動後にメインプロセスを検証します。既存ウィンドウがあれば復元を試み、前面状態を確認します。バックグラウンドのみでウィンドウがない場合も、そのまま通知します。
- 「終了（アプリのバックグラウンドを含む）」：通常終了を要求して最大 3 秒待ち、識別情報を確認した残存アプリプロセスを 1 つずつ終了します。
- 「プロセスと終了チェックを表示」：アプリプロセスと確認が必要な子タスクの名前、PID、作成時刻を表示します。
- 「緊急終了（すべての子タスクを中断）」：再確認後、更新スクリプトを含む、発見済みで識別情報を検証できるすべての子タスクを終了します。これらを明確に中断したい場合だけ使用してください。
- 「すべての Codex を終了」：結果をインスタンスごとにまとめます。失敗があっても後続のインスタンス処理は続行します。詳細は「最近の操作結果を表示」で確認できます。

<a id="更新脚本与其他子任务"></a>

## 更新スクリプトとその他の子タスク

通常終了や再起動で用途を確認できない子タスクが見つかると、終了要求を送る前に処理を阻止し、PID を一覧表示します。更新スクリプト、ターミナル、MCP サービスなどを、親子関係だけでアプリのバックグラウンドと見なすことはできません。現在、確認済みとして扱うのは、同じアプリディレクトリの Electron プロセス、Electron が直接起動した app-server、および同じディレクトリの code-mode host です。それ以外は確認が必要で、名前に update や powershell が含まれるだけでは用途を推定できません。

**このバージョンには独立した更新実行機能や自動引き継ぎインターフェースはありません。** 阻止することは引き継ぐことではなく、アプリ終了後にスクリプトが続行できる保証でもありません。インスタンスのプロセスツリーから離脱した更新スクリプトをマネージャーは自動識別できません。その更新が完了するまで再起動をクリックしないでください。新旧スクリプトが同時に更新しないよう、具体的なスクリプトと実行方法を先に確認してください。緊急終了は、インスタンスツリー内に残るタスクを明確に中断します。

<a id="更快的刷新与更稳妥的关闭"></a>

## 高速な更新と、より安全な終了

- Windows のネイティブスナップショットでプロセス関係と作成時刻を取得し、新しいアプリ識別情報を発見した場合だけ起動引数を問い合わせます。
- 引数キャッシュは PID + 作成時刻をキーとし、終了時に削除します。親 PID が再利用されても古い所属を引き継ぎません。
- プロセス、親子関係、ユーザーディレクトリの共有インデックスを構築します。通常の状態更新ではウィンドウを列挙しません。
- ウィンドウ検索、プロセス更新、終了待機、起動検証は独立したワーカースレッドで実行し、UI を同期的に待機させません。
- 既定ではメニューが閉じている間は 10 秒、開いている間は 2 秒ごとに更新します。メニューを開く、更新をクリックする、操作が完了する際も速やかに更新します。
- 終了中は検証済みプロセスのハンドルを保持し、メインプロセス終了後に孤立したバックグラウンドを追跡します。最後に既知の対象すべてを確認します。
- `taskkill /T` は使用しません。強制終了のたびに、同じプロセスハンドルで作成時刻を確認して終了を実行します。
- 操作中は重複操作を無効化し、権限エラー、終了未完了、起動タイムアウト、前面切り替え失敗を通知します。
- 1 つの起動スクリプトがなくても、トレイ全体の起動は阻止しません。該当バージョンを起動しようとした時点で具体的なエラーを表示します。

プロセススナップショットには時間的な限界があります。マネージャー起動前から孤立し、設定上の識別マーカーもないバックグラウンドの所属は、自動的には証明できません。観測した所属情報は現在のマネージャーセッション内でのみ保持し、再起動をまたいで推定しません。Windows が前面への移動を制限する場合もあるため、切り替え失敗は成功とせず通知します。

<a id="配置与诊断"></a>

## 設定と診断

`manager.settings.example.json` を `manager.settings.json` にコピーし、インスタンスディレクトリ、各バージョンの起動スクリプトとユーザーデータディレクトリ、アイコン、更新間隔、起動タイムアウトを入力します。既定のローカル設定パスは Git の無視対象ですが、追跡済み、強制追加、別名保存された個人設定を公開しないよう、コミット前にステージング領域を確認してください。最低 1 つのインスタンスが必要で、変更の反映にはマネージャーの再起動が必要です。番号、バージョン、絶対パス、ディレクトリ重複を検証します。マネージャーは起動スクリプト、アプリアーカイブ、ログイン、Codex 設定、ワークスペースを変更しません。

「診断ログを開く」で `logs` を開きます。`manager.jsonl` に操作結果、エラー、所要時間を保存し、2 MB を超えると `manager.previous.jsonl` へローテーションします。完全なプロセスコマンドラインやログイン認証情報は記録しません。設定や依存関係による起動失敗は `startup-error.log` に記録し、エラーメッセージも表示します。

<a id="常见问题"></a>

## よくある質問

**分離インスタンスの作成やアカウント切り替えもできますか？** できません。自分の起動スクリプトと独立したユーザーデータディレクトリを先に準備してください。ログイン、Codex 設定、ワークスペースは変更しません。

**マネージャーを閉じると作業中のインスタンスも終了しますか？** いいえ。トレイマネージャーの終了と Codex インスタンスの終了は別の操作です。

**通常終了が阻止されたのはなぜですか？** 用途未確認の子タスクが見つかったためです。名前、PID、作成時刻を確認し、更新、ターミナル、その他の作業か判断してください。警告を消すだけの目的で緊急終了を使わないでください。

**バックグラウンド実行中と表示されるのに、ウィンドウがないのはなぜですか？** ウィンドウのないバックグラウンドだけが残っているか、Windows が前面切り替えを制限している可能性があります。操作結果を確認してください。プロセスの存在とウィンドウの利用可能性は同じではありません。

**設定を変更しても反映されないのはなぜですか？** ローカルの `manager.settings.json` を変更したらマネージャーを再起動してください。その前に `-ValidateOnly` で番号、バージョン、パスを確認します。

**更新スクリプトを自動でマネージャーに引き継いで実行できますか？** できません。現在、独立した更新実行機能や引き継ぎインターフェースはありません。[更新スクリプトとその他の子タスク](#更新脚本与其他子任务)を参照してください。

<a id="缓存加固"></a>

## キャッシュの堅牢化

キャッシュの削除処理を識別情報の問い合わせより前に移し、部分的に成功してから例外が発生した場合でもクリーンアップを飛ばさないようにしました。各回のバックグラウンドスレッド再利用前に、エラーや警告などの診断ストリームを消去します。メインログは現行ファイルとローテーション済み 1 ファイルを保持します。起動エラーログも 256 KB を超えるとローテーションし、直前の 1 ファイルだけを保持します。最後の記録により閾値を少し超えることは許容します。

部分失敗とプロセス識別情報の変化を 1000 回連続させるリグレッションシナリオでは、旧ロジックは 1000 件蓄積しましたが、新ロジックでは現在の 1 件が最大で、すべて終了した後は 0 件になります。

<a id="安全边界"></a>

## 安全上の境界

用途を確認できない子タスクがあると通常終了は阻止されます。メニューの「緊急終了」は再確認後、そのインスタンスツリー内で発見したすべてのタスクを中断します。更新、ターミナル、その他の作業を明確に中断する必要がある場合だけ使用してください。

<a id="一起改进"></a>

## 改善への参加

対象を絞った文書修正、不具合の再現、リグレッションテストを歓迎します。プロジェクト全体を知らなくても、具体的な場面から始められます。

- 設定エラー、起動タイムアウト、切り替え失敗のメッセージを改善する。
- PID 再利用、非表示ウィンドウ、未知の子タスクなどのリグレッションテストを追加する。
- 異なる Windows 環境で操作結果を確認し、バージョンと再現手順を明記する。
- クイックスタートや診断手順を分かりやすくする。

まず「検証」と「安全上の境界」を読んでください。プロセス所属や終了ロジックの変更では、普段の作業用インスタンスを既定の対象にせず、モックと一時プロセスのテストを優先します。PR には問題、変更内容、実際に行った確認、未検証事項を記載してください。大きな動作変更は先に [Issues](https://github.com/son-gladyso/codex-tray-manager/issues) で相談してください。

実際の設定、アカウント情報、完全なコマンドライン、個人のパスを含む診断スクリーンショットは提出しないでください。識別情報の検証を緩める、確認を省く、未知のタスクを強制終了するといった方法で失敗を「修正」しないでください。
