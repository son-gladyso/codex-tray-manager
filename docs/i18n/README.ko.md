# Codex Tray Manager

[简体中文](../../README.md) · [English](README.en.md) · [日本語](README.ja.md) · [한국어](README.ko.md) · [Español](README.es.md) · [Français](README.fr.md) · [Deutsch](README.de.md) · [Português (Brasil)](README.pt-BR.md) · [Русский](README.ru.md) · [繁體中文](README.zh-TW.md)

**여러 Codex 인스턴스를 하나의 트레이에서. 창을 찾고 백그라운드 상태를 확인한 다음 종료 방법을 결정하세요.**

Windows에서 이미 격리 실행 스크립트를 사용하는 사용자를 위한 Codex Tray Manager는 실행, 전환, 다시 시작, 종료를 한곳에 모아 작업 표시줄, 스크립트, 작업 관리자를 오가는 수고를 줄입니다. 기존 인스턴스를 관리하며, 계정 생성, 채팅 이전, 격리 환경 구축은 수행하지 않습니다.

> 이 도구는 비공식 커뮤니티 도구이며 OpenAI와 제휴 관계가 없고 OpenAI의 승인을 받지 않았습니다.

Windows 10/11, PowerShell 7, 격리된 Codex 인스턴스를 실행할 수 있는 PowerShell 스크립트가 하나 이상 필요합니다. 관리자는 인스턴스마다 고유한 `--user-data-dir` 인수로 프로세스 소속을 식별합니다.

## 해결하는 문제

한 Windows 컴퓨터에서 격리된 Codex 데스크톱 인스턴스를 여러 개 실행하면 작업 표시줄, 작업 관리자, 여러 실행 스크립트를 오가야 하는 경우가 많습니다. 숨겨진 창은 찾기 어렵고, 일반 종료는 창만 닫고 백그라운드 프로세스를 남길 수 있습니다. 반대로 전체 프로세스 트리를 종료하면 앱 종료를 기다리는 업데이트 스크립트, 터미널, 기타 작업을 실수로 중단할 수 있습니다.

Codex Tray Manager는 통합 트레이 진입점을 제공하며, “앱 자체의 백그라운드 프로세스”와 “용도가 확인되지 않은 하위 작업”을 구분하여 처리합니다. 주요 해결 대상은 다음과 같습니다.

- 여러 Codex 인스턴스의 실행 상태와 조작을 한곳에서 관리하기 어려움.
- 숨겨진 창이나 창 없는 백그라운드 프로세스를 찾고 전면으로 가져오기 어려움.
- 정상 종료 후 Electron, app-server 등 백그라운드 프로세스가 남을 수 있음.
- 프로세스 트리의 무분별한 종료로 업데이트 스크립트, 터미널, 진행 중인 작업이 중단됨.
- 여러 버전의 인스턴스를 다시 시작할 때 직전에 실행하던 버전 조합을 복원하기 어려움.

<a id="功能概览"></a>

## 기능 개요

- JSON 설정에서 인스턴스 메뉴를 동적으로 만들고 실행 중인 인스턴스를 자동으로 맨 위에 배치합니다.
- 실행 후 메인 프로세스가 안정적으로 동작하는지 검증하여, 실행 스크립트의 반환값만으로 성공을 잘못 보고하지 않습니다.
- 숨겨진 Electron 최상위 창을 열거하고 복원 및 전면 전환을 시도한 뒤 결과를 확인합니다.
- 먼저 창에 정상 종료를 요청한 다음, 앱 소속으로 확인된 잔여 프로세스를 개별적으로 검증하고 정리합니다.
- PID와 생성 시각을 함께 사용하여 프로세스를 식별하고 PID 재사용으로 인한 잘못된 조작 위험을 줄입니다.
- 용도 불명의 하위 작업이 발견되면 일반 종료를 차단하고 이름, PID, 생성 시각을 표시하여 확인할 수 있게 합니다.
- 추가 확인이 필요한 긴급 종료와 인스턴스별 결과를 요약하는 일괄 종료를 제공합니다.
- `Standard`와 `UICanary` 버전을 지원하며 다시 시작할 때 이전에 실행하던 버전을 복원합니다.
- 백그라운드 스레드에서 상태를 갱신하고 종료를 기다려 트레이 메뉴의 응답성을 유지합니다.
- 자동 순환하는 JSONL 진단 로그를 기록하며 전체 프로세스 명령줄이나 로그인 자격 증명은 기록하지 않습니다.

<a id="先看一个典型使用流程"></a>

## 일반적인 사용 흐름

1. 먼저 격리 인스턴스를 하나 이상 설정합니다. 여러 개라면 각각 다른 사용자 데이터 디렉터리를 사용하는지 확인합니다.
2. 트레이에서 실행 중인 인스턴스를 확인하고 필요한 창을 전면으로 가져옵니다.
3. 종료 전에 프로세스와 종료 검사를 살펴 앱 백그라운드와 용도 미확인 하위 작업을 구분합니다.
4. 일반 종료를 사용합니다. 미확인 작업이 발견되면 긴급 종료로 우회하지 말고 원인부터 확인합니다.
5. 최근 작업 결과를 보고 실제로 무엇이 완료되었는지 확인합니다.

이 페이지에는 아직 실제 컴퓨터에서 촬영한 트레이 메뉴 스크린샷이나 영상이 없습니다. 위 내용은 작업 순서 설명이지 녹화된 데모가 아니며, 모든 실행 스크립트와 Windows 환경이 검증되었다는 뜻도 아닙니다.

<a id="快速开始"></a>

## 빠른 시작

세 가지를 먼저 준비하세요.

- Windows 10/11과 PowerShell 7(`pwsh`). 구형 Windows PowerShell만 설치되어 있으면 안 됩니다.
- 대상 Codex를 독립적으로 실행할 수 있는 기존 PowerShell 스크립트.
- 버전별 실행 스크립트의 절대 경로와 고유한 사용자 데이터 디렉터리. 예시의 `D:\codex4` 같은 경로를 그대로 복사하지 마세요.

실행 스크립트 자체가 정상 동작하지 않는다면 트레이 관리자에 연결하기 전에 먼저 해결하세요.

일반 사용자는 [Releases](https://github.com/son-gladyso/codex-tray-manager/releases)에서 Windows 포터블 ZIP을 내려받아 압축을 풀고, `manager.settings.example.json`을 `manager.settings.json`으로 복사한 뒤 로컬 경로를 입력할 수 있습니다.

개발자는 저장소를 복제해도 됩니다.

```powershell
git clone https://github.com/son-gladyso/codex-tray-manager.git
cd codex-tray-manager
Copy-Item manager.settings.example.json manager.settings.json
notepad manager.settings.json
pwsh -NoProfile -File .\CodexTrayManager.ps1 -ValidateOnly
```

검증을 통과하면 `Start Codex Tray Manager.cmd`를 두 번 클릭합니다. 관리자를 종료해도 Codex는 종료되지 않습니다.

**첫 성공의 기준:** 트레이 메뉴에 설정한 인스턴스가 표시되고 상태 갱신 후 실행 중과 중지 상태가 구분되어야 합니다. 실행 중이며 화면에 보이는 테스트 인스턴스 하나에서 “전면으로 전환”을 시도한 다음 작업 결과를 확인하세요. 설정 검증 통과는 창 전환이나 종료 동작의 실제 환경 검증 완료를 의미하지 않습니다. 먼저 검사와 결과 안내에 익숙해진 다음 종료를 시도하세요.

<a id="日常操作"></a>

## 일상적인 조작

- 설정된 Codex 인스턴스(번호 범위 4–25)를 통합 관리하고 실행 중인 인스턴스를 위에 표시합니다.
- 같은 인스턴스의 일반 버전과 UI 시험 버전을 함께 관리할 수 있습니다. 종료는 두 버전을 모두 처리하고, 다시 시작은 이전에 실행하던 버전을 복원합니다. 둘 다 중지 상태면 일반 버전을 기본 실행합니다.
- “실행 / 전면으로 전환”: 실행 후 메인 프로세스를 검증합니다. 기존 창이 있으면 복원을 시도하고 전면 상태를 확인합니다. 백그라운드는 있으나 창이 없으면 그대로 알립니다.
- “종료(앱 백그라운드 포함)”: 창에 정상 종료를 요청하고 최대 3초 기다린 후, 신원을 검증한 잔여 앱 프로세스를 하나씩 종료합니다.
- “프로세스 및 종료 검사 보기”: 앱 프로세스와 확인이 필요한 하위 작업의 이름, PID, 생성 시각을 표시합니다.
- “긴급 종료(모든 하위 작업 중단)”: 추가 확인 후 업데이트 스크립트를 포함하여 발견되었고 신원 확인이 가능한 모든 하위 작업을 종료합니다. 해당 작업을 명확히 중단하려는 경우에만 사용하세요.
- “모든 Codex 종료”: 인스턴스별 결과를 요약하며 한 인스턴스의 실패가 이후 처리를 막지 않습니다. 전체 세부 사항은 “최근 작업 결과 보기”에서 확인할 수 있습니다.

<a id="更新脚本与其他子任务"></a>

## 업데이트 스크립트와 기타 하위 작업

일반 종료나 다시 시작에서 용도를 확인할 수 없는 하위 작업을 만나면 종료 요청을 보내기 전에 차단하고 PID를 나열합니다. 업데이트 스크립트, 터미널, MCP 서비스 등을 부모-자식 관계만으로 모두 앱 백그라운드로 취급할 수는 없습니다. 현재 확인된 백그라운드는 동일 앱 디렉터리의 Electron 프로세스, Electron이 직접 실행한 app-server, 동일 디렉터리의 code-mode host입니다. 나머지는 확인이 필요하며, 이름에 update나 powershell이 포함된다는 이유만으로 용도를 추정해서는 안 됩니다.

**이 버전에는 독립 업데이트 실행기나 자동 인계 인터페이스가 구현되어 있지 않습니다.** 차단은 인계가 아니며 앱 종료 후 스크립트가 계속 실행된다는 보장도 아닙니다. 인스턴스 프로세스 트리에서 벗어난 업데이트 스크립트는 관리자가 자동으로 식별할 수 없습니다. 해당 업데이트가 끝나기 전에는 다시 시작을 누르지 마세요. 이전 스크립트와 새 스크립트가 동시에 업데이트하지 않도록 구체적인 스크립트와 실행 방식을 먼저 확인하세요. 긴급 종료는 인스턴스 트리에 남아 있는 작업을 명시적으로 중단합니다.

<a id="更快的刷新与更稳妥的关闭"></a>

## 더 빠른 갱신과 더 안전한 종료

- Windows 네이티브 스냅샷으로 프로세스 관계와 생성 시각을 가져오고, 새로운 앱 신원이 발견될 때만 실행 인수를 조회합니다.
- 인수 캐시 키는 PID + 생성 시각이며 프로세스 종료 시 제거됩니다. 부모 PID가 재사용되어도 이전 소속을 이어받지 않습니다.
- 프로세스, 부모-자식, 사용자 디렉터리의 공유 인덱스를 만듭니다. 일반 상태 갱신에서는 창을 열거하지 않습니다.
- 창 조회, 프로세스 갱신, 종료 대기, 실행 검증을 별도 작업 스레드에서 수행하여 UI가 동기적으로 기다리지 않게 합니다.
- 기본적으로 메뉴가 닫혀 있으면 10초마다, 열려 있으면 2초마다 갱신합니다. 메뉴 열기, 갱신 클릭, 작업 완료 시에도 즉시 갱신합니다.
- 종료 중에는 검증된 프로세스의 핸들을 유지하여 메인 프로세스 종료 후 고아 상태가 된 백그라운드를 추적하고, 마지막에 알려진 모든 대상을 확인합니다.
- `taskkill /T`를 더 이상 호출하지 않습니다. 모든 강제 종료는 동일한 프로세스 핸들에서 생성 시각을 검증하고 종료를 수행합니다.
- 작업 중 중복 조작을 막으며 권한 오류, 불완전한 종료, 실행 시간 초과, 전면 전환 실패를 알립니다.
- 실행 스크립트 하나가 없다고 전체 트레이 시작이 막히지는 않습니다. 해당 버전을 실행하려 할 때 구체적인 오류를 표시합니다.

프로세스 스냅샷에는 시간적 한계가 있습니다. 관리자 시작 전에 이미 고아 상태였고 설정 식별 표시도 없는 백그라운드의 소속은 자동으로 증명할 수 없습니다. 관찰된 소속은 현재 관리자 세션에서만 유지하며 관리자 재시작을 넘어 추정하지 않습니다. Windows가 전면 전환을 제한할 수도 있으므로 전환 실패를 성공으로 보고하지 않고 안내합니다.

<a id="配置与诊断"></a>

## 설정 및 진단

`manager.settings.example.json`을 `manager.settings.json`으로 복사하고 인스턴스 디렉터리, 버전별 실행 스크립트/사용자 데이터 디렉터리, 아이콘, 갱신 간격, 실행 제한 시간을 입력합니다. 기본 로컬 설정 경로는 Git에서 무시되지만, 이미 추적되거나 강제 추가되거나 별도 저장된 개인 설정이 공개되지 않도록 커밋 전에 스테이징 영역을 확인하세요. 인스턴스를 하나 이상 설정해야 하며 변경 후 관리자를 다시 시작해야 적용됩니다. 번호, 버전, 절대 경로, 디렉터리 중복을 검증합니다. 관리자는 실행 스크립트, 앱 아카이브, 로그인, Codex 설정, 작업 공간을 수정하지 않습니다.

“진단 로그 열기”는 `logs`를 엽니다. `manager.jsonl`은 작업 결과, 오류, 소요 시간을 저장하고 2 MB를 넘으면 `manager.previous.jsonl`로 순환합니다. 전체 프로세스 명령줄이나 로그인 자격 증명은 기록하지 않습니다. 설정/종속성으로 인한 시작 실패는 `startup-error.log`에 기록하고 오류 안내를 표시합니다.

<a id="常见问题"></a>

## 자주 묻는 질문

**격리 인스턴스를 만들거나 계정을 전환해 주나요?** 아니요. 직접 실행 스크립트와 독립 사용자 데이터 디렉터리를 준비해야 합니다. 관리자는 로그인, Codex 설정, 작업 공간을 수정하지 않습니다.

**관리자를 닫으면 작업 인스턴스도 종료되나요?** 아니요. 트레이 관리자 종료와 Codex 인스턴스 종료는 별개 작업입니다.

**일반 종료가 차단된 이유는 무엇인가요?** 용도 미확인 하위 작업이 발견되었습니다. 이름, PID, 생성 시각을 보고 업데이트, 터미널, 기타 작업인지 확인하세요. 경고를 없애기 위해 긴급 종료를 사용하지 마세요.

**메뉴에는 백그라운드 실행 중이라고 나오는데 왜 창이 없나요?** 창 없는 백그라운드만 남았거나 Windows가 전면 전환을 제한했을 수 있습니다. 작업 결과를 확인하세요. 프로세스가 존재한다고 창을 사용할 수 있는 것은 아닙니다.

**설정 변경이 왜 적용되지 않나요?** 로컬 `manager.settings.json`을 바꾼 뒤 관리자를 다시 시작해야 합니다. 먼저 `-ValidateOnly`로 번호, 버전, 경로를 확인하세요.

**업데이트 스크립트를 자동으로 관리자에게 넘겨 계속 실행할 수 있나요?** 아니요. 현재 독립 업데이트 실행기나 인계 인터페이스가 없습니다. [업데이트 스크립트와 기타 하위 작업](#更新脚本与其他子任务)을 참고하세요.

## 캐시 강화

식별 정보 조회 전에 캐시를 제거하도록 바꿔, 조회가 부분 성공 후 예외를 던져도 정리가 누락되지 않게 했습니다. 매 회차 백그라운드 스레드를 재사용하기 전에 오류, 경고 등의 진단 스트림을 비웁니다. 기본 로그는 현재 파일과 순환 파일 하나를 유지하며, 시작 오류 로그도 256 KB 초과 시 순환하여 이전 파일 하나만 유지합니다. 마지막 기록 때문에 기준 크기를 약간 넘는 것은 허용됩니다.

부분 실패와 프로세스 신원 변경을 연속 1000회 수행하는 회귀 시나리오에서, 이전 로직은 1000개 항목을 누적했지만 새 로직은 현재 항목을 최대 1개만 유지하고 모두 종료한 뒤에는 0개가 됩니다.

## 안전 경계

일반 종료는 용도를 확인할 수 없는 하위 작업을 만나면 차단됩니다. 메뉴의 “긴급 종료”는 추가 확인 후 해당 인스턴스 트리에서 발견된 모든 작업을 중단합니다. 업데이트, 터미널, 기타 작업을 명확히 중단해야 할 때만 사용하세요.

## 개선에 참여하기

범위가 명확한 문서 수정, 문제 재현, 회귀 테스트를 환영합니다. 프로젝트 전체를 몰라도 구체적인 상황 하나부터 시작할 수 있습니다.

- 설정 오류, 실행 시간 초과, 전환 실패 안내 개선.
- PID 재사용, 숨겨진 창, 알 수 없는 하위 작업 등에 대한 회귀 테스트 추가.
- 여러 Windows 환경에서 작업 결과를 확인하고 버전과 재현 절차 명시.
- 빠른 시작과 진단 절차를 더 쉽게 따라갈 수 있도록 개선.

먼저 “검증”과 “안전 경계”를 읽으세요. 프로세스 소속이나 종료 로직을 바꿀 때는 일상 작업 인스턴스를 기본 대상으로 삼지 말고 모의 테스트와 임시 프로세스 테스트를 우선하세요. PR에는 문제, 변경 사항, 실제 실행한 검사, 아직 검증하지 못한 부분을 설명하세요. 동작을 크게 바꾸는 경우 먼저 [Issues](https://github.com/son-gladyso/codex-tray-manager/issues)에서 논의하세요.

실제 설정, 계정 자료, 전체 명령줄, 개인 경로가 포함된 진단 스크린샷을 제출하지 마세요. 신원 검증을 약화하거나, 확인을 건너뛰거나, 알 수 없는 작업을 강제 종료하는 방식으로 실패를 “수정”해서는 안 됩니다.
