# Codex Tray Manager

[简体中文](../../README.md) · [English](README.en.md) · [日本語](README.ja.md) · [한국어](README.ko.md) · [Español](README.es.md) · [Français](README.fr.md) · [Deutsch](README.de.md) · [Português (Brasil)](README.pt-BR.md) · [Русский](README.ru.md) · [繁體中文](README.zh-TW.md)

**Несколько экземпляров Codex, один значок в области уведомлений. Найдите окно, разберитесь с фоновыми процессами и только затем решите, как завершить работу.**

Для пользователей, уже запускающих изолированные экземпляры в Windows с помощью сценариев, Codex Tray Manager объединяет запуск, переключение, перезапуск и закрытие. Так приходится реже искать нужное в панели задач, сценариях и диспетчере задач. Он управляет существующими экземплярами, а не создаёт аккаунты, переносит чаты или настраивает изоляцию за вас.

> Это неофициальный инструмент сообщества; он не связан с OpenAI и не одобрен OpenAI.

Требуются Windows 10/11, PowerShell 7 и один или несколько сценариев PowerShell, запускающих изолированные экземпляры Codex. Принадлежность процесса определяется по уникальному аргументу `--user-data-dir` каждого экземпляра.

<a id="它解决什么问题"></a>

## Какие проблемы он решает

Когда на одном компьютере Windows работают несколько изолированных настольных экземпляров Codex, приходится переключаться между панелью задач, диспетчером задач и сценариями запуска. Скрытое окно бывает трудно найти; обычное закрытие может убрать только окно, оставив фоновые процессы; завершение всего дерева процессов может случайно остановить сценарий обновления, ожидающий выхода приложения, терминал или другую задачу.

Codex Tray Manager предоставляет единый значок в области уведомлений и отдельно обрабатывает «собственные фоновые процессы приложения» и «дочерние задачи с неподтверждённым назначением». Основные проблемы:

- Отсутствие общего представления состояния и управления несколькими экземплярами Codex.
- Трудности с поиском скрытых окон и возвращением их на передний план, а также с определением фоновых процессов без окон.
- Остаточные Electron, app-server и другие фоновые процессы после нормального выхода.
- Прерывание обновлений, терминалов и текущей работы при безразборном завершении дерева процессов.
- Трудности с восстановлением ранее работающей комбинации версий при перезапуске экземпляров с несколькими версиями.

<a id="功能概览"></a>

## Обзор возможностей

- Динамически строит меню экземпляров из JSON-конфигурации и перемещает работающие экземпляры вверх.
- После запуска проверяет устойчивую работу главного процесса, а не объявляет успех только по коду возврата сценария.
- Перечисляет скрытые окна Electron верхнего уровня, пытается восстановить их и вывести вперёд, затем проверяет результат.
- Сначала запрашивает нормальный выход окна, затем отдельно проверяет и завершает остаточные процессы, принадлежность которых приложению подтверждена.
- Связывает идентичность процесса с PID и временем создания, уменьшая риск действий над повторно использованным PID.
- Блокирует обычное закрытие при обнаружении дочерних задач неизвестного назначения; показывает имена, PID и время создания для проверки.
- Предоставляет аварийное закрытие с повторным подтверждением и массовое закрытие с результатом по каждому экземпляру.
- Поддерживает версии `Standard` и `UICanary` и восстанавливает ранее работавшие версии при перезапуске.
- Обновляет состояние и ожидает завершения в фоновых потоках, сохраняя отзывчивость меню.
- Записывает автоматически ротируемые журналы JSONL, не сохраняя полные командные строки процессов или данные входа.

<a id="先看一个典型使用流程"></a>

## Типичный порядок работы

1. Сначала настройте хотя бы один изолированный экземпляр; у нескольких экземпляров должны быть разные каталоги пользовательских данных.
2. Посмотрите в меню, какие экземпляры работают, и верните нужное окно на передний план.
3. Перед выходом изучите процессы и проверки закрытия: отличайте фон приложения от дочерних задач с неподтверждённым назначением.
4. Используйте обычное закрытие. Если проверка обнаружила неподтверждённые задачи, сначала разберитесь в причине, а не обходите её аварийным закрытием.
5. Просмотрите результаты последних операций и убедитесь, что именно завершилось.

На странице пока нет снимков или записи меню на реальном компьютере. Выше описан порядок действий, а не уже записанная демонстрация; это не означает проверки всех сценариев запуска и сред Windows.

<a id="快速开始"></a>

## Быстрый старт

Подготовьте три условия:

- Windows 10/11 и PowerShell 7 (`pwsh`), а не только старый Windows PowerShell.
- Существующий сценарий PowerShell, способный самостоятельно запустить нужный Codex.
- Абсолютные пути к сценариям запуска и уникальные каталоги пользовательских данных для каждой версии. Не копируйте примеры вроде `D:\codex4` без изменений.

Если сам сценарий запуска ещё не работает, сначала исправьте его, а затем подключайте к менеджеру.

Пользователи могут скачать переносимый ZIP для Windows из [Releases](https://github.com/son-gladyso/codex-tray-manager/releases), распаковать его, скопировать `manager.settings.example.json` в `manager.settings.json` и указать свои пути.

Разработчики также могут клонировать репозиторий:

```powershell
git clone https://github.com/son-gladyso/codex-tray-manager.git
cd codex-tray-manager
Copy-Item manager.settings.example.json manager.settings.json
notepad manager.settings.json
pwsh -NoProfile -File .\CodexTrayManager.ps1 -ValidateOnly
```

После успешной проверки дважды щёлкните `Start Codex Tray Manager.cmd`. Выход из менеджера не закрывает Codex.

**Критерий первого успеха:** меню показывает настроенные экземпляры и после обновления отличает работающие от остановленных. Попробуйте «Вывести на передний план» для работающего видимого тестового экземпляра и проверьте результат. Успешная проверка конфигурации не означает приёмки переключения окон или закрытия на реальном компьютере. Сначала изучите проверки и сообщения, затем пробуйте закрывать экземпляры.

<a id="日常操作"></a>

## Повседневные операции

- Общее управление экземплярами из конфигурации с номерами 4–25; работающие показываются первыми.
- Обычная и пробная UI-версия могут управляться в составе одного экземпляра. Закрытие обрабатывает обе; перезапуск восстанавливает работавшие версии; если ни одна не работает, по умолчанию запускается обычная.
- «Запустить / Вывести на передний план»: после запуска проверяет главный процесс; существующее окно пытается восстановить и проверяет его положение. Честно сообщает, если фоновые процессы есть, а окна нет.
- «Закрыть (включая фон приложения)»: запрашивает обычный выход, ждёт до 3 секунд и по одному завершает оставшиеся процессы приложения после проверки идентичности.
- «Посмотреть процессы и проверки закрытия»: показывает имена, PID и время создания процессов приложения и дочерних задач, требующих проверки.
- «Аварийное закрытие (прервать все дочерние задачи)»: после повторного подтверждения завершает все обнаруженные дочерние задачи с проверяемой идентичностью, включая сценарии обновления. Используйте только при явном намерении прервать их.
- «Закрыть все Codex»: сводит результаты по экземплярам; сбой одного не мешает обработке следующих. Подробности доступны в результатах последних операций.

<a id="更新脚本与其他子任务"></a>

## Сценарии обновления и другие дочерние задачи

При обычном закрытии и перезапуске задачи с неподтверждённым назначением блокируют отправку запроса закрытия; менеджер показывает их PID.
Сценарии обновления, терминалы, службы MCP и подобные процессы нельзя считать фоном приложения только по связи родитель–потомок. Сейчас подтверждённый фон включает Electron из того же каталога приложения, app-server, непосредственно запущенный Electron, и code-mode host из того же каталога. Остальные процессы требуют проверки: наличие update или powershell в имени не доказывает назначение.

**В этой версии нет независимого исполнителя обновлений или интерфейса автоматической передачи управления.** Блокировка не равна передаче управления и не гарантирует продолжение сценария после выхода приложения. Менеджер не распознаёт автоматически сценарии обновления, отделившиеся от дерева экземпляра; не нажимайте перезапуск, пока такие обновления не закончены. Сначала проверьте сценарий и способ выполнения, чтобы старый и новый сценарии не обновляли одновременно. Аварийное закрытие явно прерывает задачи, остающиеся внутри дерева экземпляра.

<a id="更快的刷新与更稳妥的关闭"></a>

## Быстрее обновлять состояние, осторожнее закрывать

- Связи процессов и время создания получаются через нативные снимки Windows; аргументы запуска запрашиваются только при обнаружении новой идентичности приложения.
- Ключ кэша аргументов — PID + время создания; записи удаляются при выходе. Повторно использованный родительский PID не наследует старую принадлежность.
- Общие индексы процессов, связей и пользовательских каталогов используются совместно; обычное обновление состояния не перечисляет окна.
- Запросы окон, обновление процессов, ожидание закрытия и проверка запуска выполняются отдельными рабочими потоками; интерфейс не ждёт синхронно.
- По умолчанию обновление выполняется раз в 10 секунд при закрытом меню и раз в 2 секунды при открытом, а также сразу после открытия меню, ручного обновления и завершения операции.
- При закрытии сохраняются дескрипторы проверенных процессов, чтобы отслеживать осиротевший фон после выхода главного процесса; в конце проверяются все известные цели.
- `taskkill /T` больше не вызывается. При каждом принудительном завершении время создания проверяется и завершение выполняется через один и тот же дескриптор процесса.
- Повторные действия во время операции отключены; ошибки прав, незавершённое закрытие, тайм-аут запуска и неудачное переключение показываются пользователю.
- Отсутствие одного сценария не мешает запуску всего менеджера. При попытке запустить затронутую версию показывается конкретная ошибка.

Снимки процессов ограничены во времени. Нельзя автоматически доказать принадлежность процессов, осиротевших ещё до запуска менеджера и не имеющих конфигурационных меток. Наблюдавшаяся принадлежность хранится только в текущем сеансе и не переносится предположением между перезапусками менеджера. Windows также может ограничивать вывод на передний план: тогда показывается ошибка, а не ложный успех.

<a id="配置与诊断"></a>

## Конфигурация и диагностика

Скопируйте `manager.settings.example.json` в `manager.settings.json`, укажите каталоги экземпляров, сценарии и каталоги данных каждой версии, значки, интервалы обновления и тайм-ауты запуска. Стандартный путь локальной конфигурации исключён из Git; всё равно проверяйте индекс перед коммитом, чтобы не опубликовать уже отслеживаемую, принудительно добавленную или сохранённую в другом месте конфигурацию. Настройте хотя бы один экземпляр; для применения изменений перезапустите менеджер. Проверяются номера, версии, абсолютные пути и дубли каталогов. Менеджер не изменяет сценарии запуска, архивы приложений, данные входа, конфигурацию Codex или рабочие области.

«Открыть диагностические журналы» открывает `logs`. `manager.jsonl` сохраняет результаты, ошибки и длительность; после превышения 2 MB он ротируется в `manager.previous.jsonl`. Полные командные строки и данные входа не записываются. Сбои запуска из-за конфигурации или зависимостей сохраняются в `startup-error.log` и показываются сообщением.

<a id="常见问题"></a>

## Частые вопросы

**Создаст ли он изолированные экземпляры или переключит аккаунты?** Нет. Подготовьте свои сценарии и отдельные каталоги данных. Менеджер не меняет вход, настройки Codex или рабочие области.

**Закроет ли выход из менеджера мои рабочие экземпляры?** Нет. Это отдельные операции.

**Почему обычное закрытие заблокировано?** Найдены задачи с неподтверждённым назначением. Посмотрите имена, PID и время создания, выясните, обновления ли это, терминалы или другая работа. Не используйте аварийное закрытие только ради исчезновения предупреждения.

**Меню показывает работающий фон, но где окно?** Могли остаться только фоновые процессы без окна либо Windows ограничила переключение. Проверьте результат: существование процесса не равно доступности окна.

**Почему новые настройки не действуют?** После изменения локального `manager.settings.json` перезапустите менеджер. Сначала проверьте номера, версии и пути через `-ValidateOnly`.

**Можно ли автоматически передать менеджеру продолжение обновления?** Нет, независимого исполнителя обновлений или интерфейса передачи управления пока нет. См. [сценарии обновления и другие задачи](#更新脚本与其他子任务).

<a id="缓存加固"></a>

## Укрепление кэша

Очистка кэша перенесена перед запросами идентичности: частично успешный запрос с последующим исключением больше не пропускает очистку. Перед повторным использованием рабочего потока очищаются потоки ошибок, предупреждений и другой диагностики. Главный журнал хранит текущий и один предыдущий файл; журнал ошибок запуска также ротируется при превышении 256 KB с одной предыдущей копией. Последняя запись может немного превысить порог.

В регрессионном сценарии с 1000 последовательных частичных сбоев и изменениями идентичности старая логика накапливала 1000 записей; новая сохраняет не более 1 текущей записи, а после выхода всех процессов — 0.

<a id="安全边界"></a>

## Границы безопасности

Обычное закрытие блокируется при задачах с неподтверждённым назначением. После повторного подтверждения «Аварийное закрытие» прерывает все обнаруженные задачи внутри дерева экземпляра. Используйте его только при явном намерении прервать обновления, терминалы или другую работу.

<a id="一起改进"></a>

## Участие в улучшении

Приветствуются небольшие исправления документации, воспроизводимые сообщения о проблемах и регрессионные тесты. Можно начать с конкретного сценария без знания всего проекта:

- Улучшить сообщения об ошибке конфигурации, тайм-ауте запуска или неудачном переключении.
- Добавить тесты повторного использования PID, скрытых окон, неизвестных дочерних задач.
- Проверить результаты в разных средах Windows, указав версии и шаги воспроизведения.
- Сделать быстрый старт и диагностику понятнее.

Сначала прочтите разделы проверок и безопасности. Для логики принадлежности и закрытия предпочитайте модели и временные процессы, а не повседневные рабочие экземпляры. В PR укажите проблему, изменения, реально выполненные проверки и непроверенные случаи. Существенные изменения поведения сначала обсудите в [Issues](https://github.com/son-gladyso/codex-tray-manager/issues).

Не отправляйте реальные конфигурации, аккаунтные данные, полные командные строки или снимки диагностики с личными путями. Нельзя «исправлять» сбои ослаблением проверки идентичности, пропуском подтверждения или принудительным завершением неизвестных задач.
